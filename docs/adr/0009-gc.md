# ADR-0009: Reachability GC, emergency reserve, watermark behavior

**Status:** accepted · **Date:** 2026-08-25

## Context

Append-only immutable storage requires garbage collection. Reference counts
are optimization hints, not truth. The filesystem must never consume 100% of
backing space and then discover it lacks space to compact itself.

## Decision

- GC is mark-and-sweep (tracing): mark from **all** current roots and
  snapshots through the object graph (ADR-0007); compute per-segment live
  ratios; copy live records from low-utilization segments into a fresh
  segment; commit the new root/index; delete obsolete segments **only after**
  a durability barrier (new root durable first).
- Maintain an **emergency GC reserve** (configurable watermark, default 4%
  of physical capacity) that normal writes may not consume.
- Approaching the watermark: background GC accelerates, the foreground
  optimizer stops creating speculative alternatives, writes throttle, and
  eventually ENOSPC is returned safely — existing data is never corrupted by
  a full store.
- Derived indexes are rebuilt, not migrated, when segments are compacted.

## Consequences

- ENOSPC is precise: before accepting a transaction, EntropyFS preserves
  enough worst-case physical space for a safe commit (reserve + pending
  transaction estimate).
- GC correctness is checked by fsck's leak/unreachable report
  (`docs/recovery/fsck.md`).
