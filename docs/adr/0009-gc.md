# ADR-0009: Reachability GC, emergency reserve, watermark behavior

**Status:** accepted · **Date:** 2026-08-25

## Context

Append-only immutable storage requires garbage collection. Reference counts
are optimization hints, not truth. The filesystem must never consume 100% of
backing space and then discover it lacks space to compact itself.

## Decision

- GC is mark-and-sweep (tracing): mark from **all** current roots and
  snapshots through the object graph (ADR-0007); compute per-segment live
  ratios; copy live records from low-utilization segments into a fresh
  segment; commit the new root/index; delete obsolete segments **only after**
  a durability barrier (new root durable first).
- Maintain an **emergency GC reserve** (configurable watermark, default 4%
  of physical capacity) that normal writes may not consume.
- Approaching the watermark: background GC accelerates, the foreground
  optimizer stops creating speculative alternatives, writes throttle, and
  eventually ENOSPC is returned safely — existing data is never corrupted by
  a full store.
- Derived indexes are rebuilt, not migrated, when segments are compacted.
  **Phase-9H**: the chunk-index rebuild bulk-loads the tree bottom-up from
  sorted reachable entries (`index::bulk_load`), staging each final node
  exactly once — the earlier repeated-COW-insert rebuild physically wrote
  and indexed every intermediate path version (2.66 MB of dead BtreeNode
  records on the real-tree court).
- **Phase-9H**: per-segment live ratios are PHYSICAL — the denominator is
  every valid record scanned from the segment file (including records the
  derived object index no longer represents), not the index's one-location
  view; victim selection therefore compacts segments whose physical
  occupancy is dominated by garbage even when the index calls them live.
- **Phase-9H**: `compact_full` (`entropyfs gc --compact`) treats every
  segment as a victim, converging the physical backing to the reachable
  persistent state plus bounded format overhead; it is idempotent (a
  second run reclaims ~nothing). The current root record is not
  re-copied (the pass writes a fresh root); snapshot roots are Root
  records too and are still copied.

## Consequences

- ENOSPC is precise: before accepting a transaction, EntropyFS preserves
  enough worst-case physical space for a safe commit (reserve + pending
  transaction estimate).
- GC correctness is checked by fsck's leak/unreachable report
  (`docs/recovery/fsck.md`).
- **The chunk index is derived, not authoritative (Phase 5)**: its tree
  nodes stay root-reachable, but the objects its entries reference are
  pinned only when the content id is referenced by a live extent (an
  `EXACT_REF` target or a `BASE_RESIDUAL` base). Otherwise the ever-growing
  dedup index would pin deleted data forever and GC could never reclaim it.
  A future write whose dedup hit was collected simply falls back to RAW
  (the index entry is rewritten).
- Snapshots pin their roots through the snapshot tree; `restore_snapshot`
  rolls the current root back to a snapshot's root with a monotonic
  generation bump and re-inserts the restored-from snapshot (ZFS-style).
  Deleting a snapshot immediately unpins its objects for the next GC pass.
  Crash-court tests cover snapshot create/delete/restore at every
  durability boundary.
